| 2026-10-07 | Notion | Database formulas (the formula property: typing `prop("Hours") * prop("Rate")` into a column so every row computes itself and stays correct when an input changes), NOT database views/filters (08-02) and NOT the slash command/block model (06-25). A formula column is TWO problems stitched together: a tiny LANGUAGE (tokenize text -> typed AST -> evaluate per row; parse once, evaluate often) and, the heart, a DEPENDENCY GRAPH + incremental recompute. Real example: Rohan's Invoices DB, Amount=Hours*Rate, Tax=Amount*0.18, Total=Amount+Tax, plus a rollup "Total billed" through a relation to Clients; he changes Hours 10->12 and Amount, Tax, Total AND the client rollup all fix themselves while the other 239 invoices sit still. The magic = NEVER recompute the whole table: model every formula cell as a node with an arrow to each cell it reads = a directed ACYCLIC graph (DAG), then on an edit do 3 moves (CONFIRMED for Excel via Microsoft recalc docs; INFERENCE for Notion, which has not published the formula engine, clearly labeled): (1) MARK DIRTY, follow arrows out of the changed cell and transitively mark every downstream cell (Hours->Amount->{Tax,Total,rollup}, Tax->Total), untouched rows never reached = zero work; (2) ORDER by TOPOLOGICAL SORT of just the dirty subgraph (Kahn: repeatedly take a cell whose inputs are all ready) = Amount then Tax then Total, Excel's "calculation chain in the order in which they should be calculated"; (3) EVALUATE in order, each dirty cell computed exactly once, cost proportional to cells CHANGED not database size (HotXLS: cost tracks dirty cells not workbook size). Why a DAG not a list/hashmap: a list loses ordering, a hashmap gives O(1) formula lookup but no "what follows what", so keep both (hashmap for where-is-this, edges for what-follows-this). CYCLES = the one rule to refuse: a self-referential formula has no valid topo start, detect at EDIT TIME and error (Excel "detects the circular reference and warns"; same as Figma rejecting a cyclic reparent 10-04). Relations/rollups = edges crossing databases (an aggregation node summing many inputs); Formulas 2.0 (CONFIRMED, Sept 2023) made cross-DB reads first class + rich types (pages/dates/people/lists) + lets()/map() = a real extensible language with a typed AST. WHERE it runs (well-grounded INFERENCE, not published): client-heavy, the AST evaluates in the browser/app over LOADED rows (results update live as you type, no round trip), server stores inputs as blocks and caches derived values = the INPUTS are truth, the derived value is a CACHE. The spine: a voice note is a tiny audio-compression problem + a media-encryption problem + a blob-delivery problem stitched together, and the clever part is WHERE each piece of work runs. The one decision that makes it feel free = the CODEC: WhatsApp records in OPUS inside an Ogg container (CONFIRMED, Meta developer docs require `.ogg`+Opus, the exported file is `.opus`/`.ogg`), speech-tuned mono at a low bitrate (~16-32 kbit/s, measured not published = INFERENCE), which turns a 40-second clip from ~7 MB of raw CD-style audio into ~120 KB, roughly a SIXTYFOLD shrink, and THAT ratio is why a voice note is as cheap to send as a text and still works on 2G where most of 2B users live. Opus chosen for 3 reasons: beats MP3/AAC at low bitrate for speech (RFC 6716, 6-510 kbit/s, 8-48 kHz), encodes in tiny frames so the phone compresses WHILE you talk (streaming, not a big post-stop encode), and it is the shared language every client must agree on because END-TO-END ENCRYPTION means the server NEVER sees the audio and so CANNOT transcode in the cloud the way a normal media app does = the privacy guarantee removes cloud transcode and pushes encode+decode onto the phones (same edge-work theme as the whole ledger). Media encryption flow (CONFIRMED, WhatsApp Encryption Overview whitepaper): phone generates an EPHEMERAL 32-byte AES-256 key + 32-byte HMAC-SHA256 key per clip, encrypts the Opus file AES-256-CBC with random IV, appends an HMAC over the ciphertext, uploads the ENCRYPTED blob over plain HTTPS to a dumb blob store, gets a URL, then sends the receiver a normal Signal-protocol E2E chat message carrying ONLY {mediaUrl, mediaKey, mac, sha256, durationSeconds, waveform[]} = the HEAVY audio bytes go over cheap HTTPS to a blob store, only the small SECRET (keys+URL+hash) rides the expensive E2E message channel = the exact control-plane/data-plane (presigned-URL) split from large-file-upload, keep big bytes off the sensitive path. Data structures: the Opus/Ogg file = an ARRAY of few-millisecond frames in Ogg pages (2x playback = decode same frames, resample output faster, hold pitch, re-download nothing); the waveform under the bubble = a tiny ~50-100 number amplitude array computed on the phone and shipped inside the small message (a visual summary, NOT the audio); the message record = a small hash-map of fields so the body stays tiny though the content is 40s of talking; a local outbox/retry queue drives the clock->one-tick->two-tick ladder on a patchy network. WHERE work happens (the scale-defining choice) = NOTHING expensive touches the server per clip: encode on sender phone, decode+speed+transcript on receiver phone, server just stores+serves an opaque blob and routes a small message. Retention = the "say it don't type it" HABIT loop (thumb goes to mic not keyboard the moment you have more than a sentence), moves retention+engagement not revenue, and the 2022 bundle (out-of-chat playback, 1.5x/2x holding pitch, pause/resume record, draft preview, remember-where-you-stopped) + 2024 on-device transcripts are each a retention move dressed as convenience = protect the habit by removing the friction of RECEIVING a note; 7B/day proves it is core daily behavior for a big slice of 2B people.
