The split that organizes everything = limiters 1-2 ask "is this CALLER behaving?" while load shedders 3-4 ignore the caller and ask "is the whole SYSTEM healthy right now?" (different question, different tool), and they run cheapest-and-account-specific FIRST so the common case (one merchant's runaway retry loop) is refused at gate 1 for almost nothing while the rare case (whole fleet underwater) is caught at gates 3-4. (1) REQUEST RATE LIMITER = a TOKEN BUCKET in Redis (example: refill 100 tokens/sec, capacity 500, so a caller sustains 100/s forever AND can burst 500 instantly because real clients are bursty not abusive = a merchant quiet for 4s then firing 400 in one second is normal), enforced by an ATOMIC Lua script (the whole trick: two concurrent requests can never both read "1 token left" and both spend it), returns 429; the Redis key gets a TTL of fill_time*2 so idle accounts cost no memory and a returning caller starts fresh (same let-it-expire discipline as Stories expiry and seat locks); the open-source `throttled` (Go) was rewritten from a naive counter to GCRA (Generic Cell Rate Algorithm) = store exactly ONE timestamp per key (the "theoretical arrival time", earliest the next request is allowed), compare now against it, push it forward = one number, one comparison, one write, no background drip process = why it scales to millions of keys as millions of tiny independent timestamps in a hash map (which is exactly what Redis is). (2) CONCURRENT REQUESTS LIMITER = counts IN-FLIGHT not arriving, because 20 req/s each taking 10s = 200 held-open workers starves the fleet at a rate no rate-limiter would flag; data structure = a Redis SORTED SET per account (add request id scored by timestamp on start, remove on finish, read size with ZCARD vs a cap of 100, trim entries older than a 60s TTL), NOT a plain integer counter because a counter cannot self-heal a crashed client's leaked slot = the sorted set encodes both "how many" and "since when" so you can atomically drop everything older than 60s and the count corrects itself. (4) WORKER UTILIZATION LOAD SHEDDER = the floor; each worker box watches its own CPU and, past sustained saturation, independently begins rejecting the least-critical work with a probability that RAMPS UP gradually (example: holds off ~28s before shedding, ramps to full over ~120s) so a 2s spike is not a cliff but a real overload gets firm backpressure. Two invariants across all four: the guard MUST be cheaper than the work it guards (an in-memory timestamp comparison, one number per key) or refusing becomes the bottleneck it was meant to prevent, and it MUST FAIL OPEN (Stripe observed Redis unavailable ~0.01% of the time and simply allows traffic through rather than blocking money movement on a cache). Why all four in this order: rate limiter catches one caller too fast, concurrent limiter catches one caller holding too many slow requests at a LEGAL rate, fleet shedder catches global load with no single guilty caller (protect money over reads), worker shedder catches the infrastructure itself dying; remove any one and a whole class of outage returns. Scale story (what grows is REQUESTS/SEC and distinct keys, NOT a catalog of items): 1k/s = one Redis node, every check one atomic Lua script sub-millisecond, you could almost skip the shedders, do NOT over-engineer; 100k/s = a single Redis node's CPU/network + memory (hundreds of thousands of live buckets/sorted-sets) strain, fixed because limiter state is embarrassingly shardable = hash the keyspace by account id across a Redis cluster (Priya's bucket on node 7, the bakery's on node 12, never contend = the same "the key routes itself so sharding is free" property as Stripe idempotency keys + Notion blocks), TTL cleanup keeps memory bounded by ACTIVE not total callers; 10M+/s on a sale day = two hard things: (a) HOT KEY (one giant merchant = one account id = all its limiter traffic on one shard = that shard is the ceiling, the same wall as Amazon Lightning Deals' single stock counter), inference-level fix = split one account into N sub-buckets acct:123:bucket:0..9 across shards, trade exact accounting for a 10x contention drop, and (b) the real reason the shedders exist = at this tier the danger is no longer any one caller but AGGREGATE global load + correlated failure (a slow dependency in the exact minute of peak), per-account limits do nothing because everyone is individually behaving, only the fleet + worker shedders survive by shedding the least-important slice of a fundamentally oversubscribed fleet.
